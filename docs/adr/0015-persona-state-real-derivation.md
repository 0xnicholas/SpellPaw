# Persona/State real derivation: dual-path alignment, not a new trigger

M7 upgrades the Customer Graph's Persona/State from a rule-based stub to real derivation. The derivation architecture **reuses the ADR-0003 dual-path precomputation layer** (event-triggered incremental + dirty-flagged batch) rather than introducing a new trigger mechanism. State (rules, cheap, real-time) stays on the incremental path; Persona (LLM, expensive) runs only on the batch path. Risk/Opportunity scoring uses transparent, env-tunable heuristics (a convenience layer over raw signals, not empirically calibrated); the pgvector-backed Intent Vector is deferred until a similarity-search consumer exists. Because Persona derivation egresses customer message content to the user's BYOK LLM, it is gated behind a new `Workspace.personaDerivationEnabled` toggle (default off, mirroring ADR-0014's `mcpInboxAccess`). M7 ships in two tranches: M7-A/B (State rules + the `complete()` primitive) now against any data; M7-C (Persona derivation pipeline) is built against mock for plumbing only, with M7-D (State←Persona coupling + Persona UI exposure) deferred until real X data validates derivation quality.

**Why**: ADR-0012 defines Persona/State as *the product*, but the code ships only a stub — `recomputeContactState` implements AWARE→ENGAGED + manual ACTIVATED (the comment reads "No signals yet for LOYAL/AT_RISK/CHURNED"), `stateRiskScore`/`stateOpportunityScore` are never written, and `personaSentimentArc`/`personaIntentVector` are permanently null. Two architectural questions had to be settled before implementation: (1) how derivation is triggered, and (2) whether State and Persona share a path. Reusing ADR-0003 answers both — it already specifies event-triggered incremental updates for real-time needs and a dirty-flagged batch pass for expensive cross-record derivations like Content DNA. Putting Persona derivation on a per-click event path would call an LLM on every Content Touch (cost + latency on the Inbox open path); putting State on the batch path would make a contact's stage/risk stale for up to an hour. Splitting them along the existing ADR-0003 seam avoids both.

**Considered alternatives**: (a) Daily scheduled recompute of all "active" contacts (the initial proposal). Rejected in favor of ADR-0003's dirty-flag scan — recomputing contacts with no new interactions is wasted work, and the dirty flag is already the documented mechanism. (b) On-demand/TTL derivation triggered by `contact.get`. Rejected — it injects LLM latency and cost variance into the read path, violating "Persona is always a background-filled field." (c) Enabling pgvector now and storing real Intent embeddings. Rejected — Phase 1 has no similarity-search consumer (Inbox shows a single contact's persona, not "find similar contacts"), enabling it would couple Phase 1 to OpenAI embeddings (Anthropic has none) and require a risky column-type migration (`DOUBLE PRECISION[]` → `vector(1536)`, extension never enabled). A readable `personaIntent Json?` delivers the displayable value now; the vector slot stays for later. (d) For the Persona content-egress PII question: riding on BYOK consent (user supplied the key ⇒ consented to egress). Rejected — Composer already egresses the user's *own* Post text under BYOK, but Persona derivation egresses *customer* message content (a third party's, possibly PII-laden DMs), a categorically more sensitive egress the user may lack consent to make. Regex-PII-scrubbing before egress was also rejected — ADR-0014 already ruled "content redaction is fragile (regex-based cleaning misses)." A workspace-level gate (default off) is the consistent choice.

**Consequences**:
- Two backward-compatible nullable columns added to `Contact` (`personaDirtyAt DateTime?` batch-scan flag, `personaIntent Json?` readable intent) plus one `Workspace` gate field `personaDerivationEnabled Boolean @default(false)`. `stateRiskScore`/`stateOpportunityScore`/`personaSentimentArc` begin being written; `personaContentDNA` is upgraded from rule counts to real Content DNA. `personaIntentVector` stays as-is (pgvector deferred).
- The "ACTIVATED sticky" semantics are clarified and locked: activation is a one-way ratchet against *engagement* decay (never drops back to ENGAGED/AWARE), but is still subject to *risk* decay (→ AT_RISK → CHURNED). LOYAL is not sticky. AT_RISK recovery is a forward recompute from the ACTIVATED baseline; CHURNED recovery returns to AWARE.
- State recomputation stays inline-synchronous on Interaction writes (and on a daily decay cron for time-driven At Risk/Churned). Persona derivation runs on a BullMQ repeatable job (`PERSONA_BATCH_CRON`, default hourly per ADR-0003) scanning `personaDirtyAt IS NOT NULL`.
- Two PII risks are distinguished: (a) *exposure* — derivation output is exposed only through `NON_PII_SELECT` (no `profile_*`); (b) *egress* — derivation reads Conversation/Post text and sends it to the BYOK LLM, which `NON_PII_SELECT` does not cover. The egress path is gated by `personaDerivationEnabled` (default off); when off, no customer content is read or sent. This corrects the v1 design's conflation of the two.
- Degradation is first-class: gate off → no derivation, no content egress, dirty retained; no BYOK key (gate on) → write rule-based fallback Persona and clear dirty (no retry storm); AI failure → keep prior Persona, leave dirty (BullMQ backoff retries). The read path never blocks on AI.
- Sequencing: M7-A (State rules + daily decay cron) and M7-B (`complete()` refactor) ship now — State rules are data-agnostic. M7-C (Persona pipeline) is built against mock for plumbing validation only; M7-D (State←Persona coupling + Persona UI exposure) is deferred until X real-data integration lands and derivation quality is validated, to avoid surfacing unvalidated "insights" as authoritative.
- Documented simplifications (per-Contact Content DNA normalization, no pgvector, transparent scoring) carry explicit upgrade paths in the design doc; moving off any of them requires a follow-up ADR.
